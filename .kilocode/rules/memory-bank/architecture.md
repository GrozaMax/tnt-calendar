## Ключевые технические решения

### 1. Асинхронная архитектура

Все обработчики используют `async/await` для неблокирующей работы:
```python
async def start_command(update: Update, context: ContextTypes.DEFAULT_TYPE):
    await update.message.reply_text("Hello!")
```

**Причина**: Telegram Bot API работает асинхронно, это позволяет обрабатывать множество запросов одновременно без блокировки.

### 2. Класс TelegramBot

Инкапсулирует всю логику бота в одном классе:
- Инициализация Application
- Регистрация обработчиков
- Запуск polling

**Причина**: Упрощает управление жизненным циклом бота и делает код более организованным.

### 3. Модульная структура обработчиков

Обработчики команд вынесены в отдельный модуль `handlers/`:
- `base.py` - базовые команды
- В будущем: `calendar.py`, `events.py`, `notifications.py`

**Причина**: Разделение ответственности, легкость в добавлении новых команд.

### 4. Централизованная конфигурация

Класс `Config` в `src/config.py`:
- Загрузка переменных окружения
- Валидация конфигурации
- Типизированный доступ к настройкам

**Причина**: Единая точка управления конфигурацией, легкость в тестировании.

### 5. Обработка ошибок

Глобальный обработчик ошибок `error_handler`:
- Логирование ошибок
- Отправка понятных сообщений пользователю
- Предотвращение падения бота

**Причина**: Стабильность работы, удобство отладки.

## Паттерны проектирования

### Command Pattern
Каждая команда бота - это отдельная функция-обработчик:
```python
async def start_command(update: Update, context: ContextTypes.DEFAULT_TYPE):
    # Обработка команды /start
```

### Singleton (Config)
Класс конфигурации использует class methods для доступа к настройкам:
```python
Config.BOT_TOKEN  # Доступ к токену
Config.validate()  # Валидация
```

## Критические пути выполнения

### Запуск бота
1. `main.py` → `main()`
2. Создание экземпляра `TelegramBot()`
3. `Config.validate()` - проверка конфигурации
4. `Application.builder().token().build()` - создание приложения
5. `_register_handlers()` - регистрация обработчиков
6. `run_polling()` - запуск получения обновлений

### Обработка команды
1. Telegram отправляет обновление
2. `Application` получает обновление через polling
3. Роутинг к соответствующему `CommandHandler`
4. Вызов асинхронной функции-обработчика
5. Отправка ответа пользователю

### Обработка ошибки
1. Исключение в обработчике
2. `error_handler` перехватывает ошибку
3. Логирование в консоль
4. Отправка сообщения об ошибке пользователю

## Взаимосвязи компонентов

- `main.py` зависит от `src.bot.TelegramBot`
- `TelegramBot` зависит от `src.config.Config` и `src.handlers.base`

## Технические ограничения

1. **Telegram API Rate Limits**: 
   - 30 сообщений в секунду на бота
   - 20 сообщений в минуту в одну группу

2. **Python-telegram-bot**:
   - Требует Python 3.9+
   - Асинхронная модель выполнения

3. **Polling vs Webhooks**:
   - Текущая реализация использует polling
   - Для production рекомендуется webhooks

## Принципы разработки

1. **KISS (Keep It Simple, Stupid)**: Простота кода важнее сложных оптимизаций
2. **DRY (Don't Repeat Yourself)**: Переиспользование кода через функции и классы
3. **Separation of Concerns**: Разделение на слои (handlers, services, data)
4. **Fail Fast**: Валидация конфигурации при запуске
5. **Explicit is better than implicit**: Явная типизация и понятные имена
